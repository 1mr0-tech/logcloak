Hands-on guide

Install logcloak, verify masked output

A complete walkthrough — from a bare cluster to verified masked logs. Every command and output below is real, captured from a live k3s/k3d cluster.

Prerequisites

  • Kubernetes 1.24+ (k3s, GKE, EKS, or AKS)
  • Helm 3.x

1. Install logcloak

Add the repo and install the chart into its own namespace:

helm repo add logcloak https://1mr0-tech.github.io/logcloak
helm repo update
helm install logcloak logcloak/logcloak \
  --namespace logcloak --create-namespace

Verify both containers (webhook + controller) are running in each pod:

kubectl get pods -n logcloak
# NAME                        READY   STATUS    RESTARTS   AGE
# logcloak-68c64b8fb4-67gmb   2/2     Running   0          50s
# logcloak-68c64b8fb4-bj6gp   2/2     Running   0          50s

TLS needs no configuration. logcloak generates a self-signed certificate on first startup, stores it in a Secret, and patches its ownMutatingWebhookConfiguration with the CA. The cert is valid for one year and rotates automatically before expiry — track time-to-expiry with thelogcloak_tls_cert_expiry_seconds Prometheus gauge.

A PodDisruptionBudget (minAvailable: 1 by default) ships with the chart, and both webhook and controller emit structured JSON logs. Prometheus metrics are on port 9090 — see the docs page for the full metric reference.

2. Opt a namespace in

logcloak is opt-in. Only labelled namespaces get sidecar injection — this keeps system namespaces untouched.

kubectl create namespace production
kubectl label namespace production logcloak.io/inject=true
Any pod created from this point forward gets the sidecar injected automatically. Existing running pods are unaffected until restarted.

Choosing your masking approach

logcloak has two ways to define what gets masked. Use them together — annotations extend a policy, they never remove rules from it.

MaskingPolicyPod annotation
Who sets itPlatform / security teamDeveloper
ScopeAll matching pods in a namespaceOne pod only
Can override policy?—No — extends, never removes
Requires cluster access?YesNo — just deployment YAML

3. MaskingPolicy (platform team)

A MaskingPolicy defines masking rules for pods matching a selector in a namespace. No selector means every pod in the namespace.

# masking-policy.yaml
apiVersion: logcloak.io/v1alpha1
kind: MaskingPolicy
metadata:
  name: pii-baseline
  namespace: production
spec:
  patterns:
    - name: email
      builtin: email
    - name: phone
      builtin: phone-e164
    - name: otp
      builtin: otp-6digit
    - name: auth-token
      regex: 'Bearer\\s+[A-Za-z0-9\\-._~+/]+=*'
  redactWith: "[REDACTED]"
kubectl apply -f masking-policy.yaml
# maskingpolicy.logcloak.io/pii-baseline created

Built-in pattern names

emailRFC 5321 email addresses
phone-e164E.164 international phone numbers
phone-usUS phone number formats
otp-6digitStandalone 6-digit numeric codes
credit-card13–19 digit card numbers
jwteyJ… JWT tokens
ipv4-privateRFC 1918 private IP addresses
uuidUUID v4
ibanInternational Bank Account Numbers
ssnUS Social Security Numbers (XXX-XX-XXXX)

Targeting specific services with a selector

spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: payment-service
  patterns:
    - name: credit-card
      builtin: credit-card

4. Pod annotations (developer)

Developers extend masking with app-specific patterns, without touching the cluster-wide policy.

Field masking recurses into nested objects and arrays, runs before regex rules, and applies to lines that begin with {. You can combine all three on one pod:

annotations:
  logcloak.io/patterns: "email,jwt"
  logcloak.io/fields: "password,secret,api_key"
  logcloak.io/regex-order-id: 'ORD-[0-9]{8}'

Field masking also works as a cluster-wide MaskingPolicy rule:

spec:
  patterns:
    - name: password-field
      field: password
    - name: token-field
      field: api_token

5. Verify raw logs are clean

Confirm raw PII never reached the node's log files:

sudo grep -r 'user@shop.com\|card=4111\|otp=847291' /var/log/containers/ 2>/dev/null | wc -l
# 0

6. Reject invalid regex at admission

Custom regex is validated at pod admission time. Unsafe patterns (lookaheads, backreferences) are rejected before the pod ever starts:

kubectl run bad-pod -n production --image=busybox:1.36 \
  --annotations='logcloak.io/regex-bad=(?=lookahead)' -- sh -c 'echo test'

# Error from server: admission webhook "mutate.logcloak.io" denied the request:
# invalid regex in annotation "logcloak.io/regex-bad": unsafe regex construct "(?=" detected

Audit logs before you deploy

logcloak scan checks what PII is currently leaking from any log source — no cluster required. Install the CLI binary from the GitHub releases page.

kubectl logs my-pod | logcloak scan
logcloak scan /var/log/app.log
line 42     user [REDACTED:email] placed order        [email]

logcloak scan summary
Total lines:     1234
Lines with PII:  1 (0.1%)
Pattern hits:
  email:               1

Protect these logs → kubectl label namespace <ns> logcloak.io/inject=true

Check a MaskingPolicy for coverage gaps

scan tells you what PII exists in a log source. logcloak audit tells you whether a specific MaskingPolicy you're about to apply would actually catch it — before you deploy it. It compiles the policy's configured builtin patterns, runs them alongside the full built-in library against the same sample, and shows exactly what kubectl logs would still expose.

logcloak audit masking-policy.yaml /var/log/app.log
line 42     Processing payment for [REDACTED] card=4111111111111111 otp=[REDACTED]  [MISSING: credit-card]

logcloak audit summary — policy: masking-policy.yaml
Total lines:              1234
Lines masked by policy:   3
Lines with exposed PII:   1 (0.1%)
Missing built-in patterns:
  credit-card:         1 line(s)

Add these to masking-policy.yaml → spec.patterns:
  - name: credit-card
    builtin: credit-card

Also available: logcloak validate '<regex>' to check RE2-safety before deploying, and logcloak preview '<regex>' [file] to test masking output without touching a cluster.

7. Service mesh compatibility

logcloak is safe alongside Istio, Linkerd, and any other mesh — meshes intercept network traffic; logcloak intercepts stdout. These containers are always skipped: istio-proxy, linkerd-proxy, envoy, envoy-sidecar, kuma-sidecar, consul-sidecar, vault-agent, config-reloader.

For anything else (a postgres sidecar, a monitoring agent), exclude it explicitly:

metadata:
  annotations:
    logcloak.io/exclude-containers: "postgres,redis,datadog-agent"

kubectl logs behaviour reference

kubectl logs <pod>Masked output (logcloak is the default container)
kubectl logs <pod> -c logcloakSame masked output
kubectl logs <pod> -c appEmpty — app stdout is redirected to the FIFO

Uninstall

helm uninstall logcloak -n logcloak
kubectl delete crd maskingpolicies.logcloak.io
kubectl delete namespace production

Helm never deletes CRDs on uninstall — that's Helm's own behaviour, not logcloak's, so the explicit kubectl delete crd step above is required if you want MaskingPolicy resources gone too. Already-injected pods keep running with their sidecar until restarted.
